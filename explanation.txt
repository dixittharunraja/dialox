DIALOX - APPLICATION NEED AND CURRENT STATE
================================================================================

PROJECT OVERVIEW
================================================================================
Dialox is a phone-number-first email platform built for the Alphastack 7-day
buildathon. The core innovation: every verified phone number becomes a real
mailbox at the service domain, e.g., +91 98765 43210 → 9876543210@dialox.local.

Users can:
- Sign up via IVR call, SMS, or a web portal (no email required)
- Receive mail over SMTP from anywhere
- Send mail via two native clients: a WhatsApp-styled mobile app and a
  Gmail-styled web client
- Access their inbox from any device, with automatic SMS alerts when offline


WHY THIS APPLICATION EXISTS
================================================================================

Problem Statement:
-------------------
Traditional email assumes users have an email address before they can receive
mail. This creates friction for:

1. Users in emerging markets where SMS/phone calls are ubiquitous but email
   adoption is low
2. People without stable internet who primarily use feature phones
3. Anyone who wants a secondary inbox tied to their phone number (for alerts,
   OTPs, notifications)
4. Organizations sending time-sensitive mail to phone-based identities

Current Email Limitations:
- Signup requires an existing email or social account
- Recovery relies on email (circular dependency)
- No native phone-number identity; phone is just a recovery channel
- SMS is used for notifications, not as a primary interface
- Inbox/Sent split feels unnatural for chat-like conversation flow

Dialox Solution:
- Phone number IS the email address (no separate username/password)
- Sign up in 30 seconds via phone call or SMS (works on any phone)
- Receive mail over SMTP; send via app or SMTP
- One unified "chat" view (no Inbox/Sent split), matching user expectations
- SMS notifications when app is not in use
- Forward/reply with full threading and recipient locking (no accidental CC)


TARGET USE CASES
================================================================================

1. Emerging Market Notifications
   A fintech app in India wants to send transaction alerts. Instead of asking
   users for an email, it sends to +91 98765 43210@dialox.local. The user sees
   the alert as an SMS if they're not in the app, and as a message in Dialox
   if they are.

2. Two-Factor Authentication
   Services can send OTP codes to phone-based mailboxes, giving users an
   audit trail they can check later (not just ephemeral SMS).

3. Secondary Inbox
   Power users who want a "phone inbox" for alerts/notifications separate
   from their work email, without managing another email account.

4. Feature Phone Users
   Billions of people use feature phones. Dialox's SMS signup and IVR support
   mean they can access email without a smartphone or internet connection.

KEY DECISIONS & TRADEOFFS
================================================================================

1. One SPA, Not Four Apps
   Decision: Build a single Vite app with lazy-loaded surfaces (mobile, web,
   portal, simulator) rather than four separate apps.
   Tradeoff: Code sharing is easier; bundle is larger than if mobile-only.
   Reality: Main bundle is 290 KB (gzipped), mobile chunk is 55 KB; negligible.

2. Chat Model for Email
   Decision: One conversation per (owner, participants) instead of Inbox/Sent.
   Tradeoff: More intuitive for chat-like flows; unfamiliar for traditional
   email users.
   Reality: Solved by showing all mail (sent + received) in chronological order,
   one conversation per unique participant set.

3. Reply-Once Enforcement
   Decision: Unique index on (sender_user_id, in_reply_to_id) enforces that
   each sender can reply to a message only once.
   Tradeoff: Prevents accidental double-replies; matches WhatsApp behavior.
   Reality: UI prevents it too, database is the safety net.

4. SMS Notifications Only When Offline
   Decision: Check if user has an active mobile session before sending SMS.
   Tradeoff: Users who leave the app running won't get SMS (by design).
   Reality: Saves SMS cost and respects user intent (if app is open, they see
   mail immediately).

5. PGlite Fallback for Local Dev
   Decision: When DATABASE_URL is unset, use embedded Postgres (PGlite).
   Tradeoff: No external database needed; perfect for testing. Real Postgres
   required for production.
   Reality: Developers can `pnpm dev` without Docker or a database server.

6. API Port 4000 (Not 3000)
   Decision: Use port 4000 because user's Next.js projects use 3000.
   Tradeoff: One extra config line; clearer separation.
   Reality: Avoids port conflicts, cleaner local development.
